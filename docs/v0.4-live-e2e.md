# v0.4 真机外实时端到端（Live E2E）验证

本文记录 `app/src/test/java/top/qiuli55/fluxbot/data/live/LiveE2ETest.kt` 的设计、运行方式与实测结果。该测试在 JVM 上直接运行 App 的生产代码（`CloudAuthManager`、`CloudClient`、`Api`、`ApiV040` 里的解析器、`SecureCloudTokenStore`），打真实的本地 Flux Cloud 与 flux-bot 服务，不使用任何 mock，也不依赖 Robolectric。

没有设置 `FLUXBOT_LIVE_CLOUD` 与 `FLUXBOT_LIVE_BOT` 时测试通过 `Assume.assumeTrue` 直接跳过，CI 与普通本地构建不受影响。

## 测试环境

| 组件 | 地址 | 说明 |
| --- | --- | --- |
| Flux Cloud 本地副本 | `http://127.0.0.1:18500` | 与生产同一份源码，全新空库，测试专用密钥；关闭限流、开放注册 |
| flux-bot | `http://127.0.0.1:18700` | origin/main `753b155` 构建的镜像，信任上述 Cloud 副本签发的 access token |

Bot 在 Docker 里运行，客户端来源不是回环地址，所以 `require_rest_auth` 真正生效，可以用 401 验证刷新链路（本机直连时部分接口会走回环豁免，反而测不到）。

## 运行方式

```bash
export ANDROID_HOME=/opt/android-sdk ANDROID_SDK_ROOT=/opt/android-sdk GRADLE_USER_HOME=/home/box/.gradle-flux
export FLUXBOT_LIVE_CLOUD=http://127.0.0.1:18500
export FLUXBOT_LIVE_BOT=http://127.0.0.1:18700
./gradlew --no-daemon testDebugUnitTest --tests '*Live*' -i
```

测试会打印一张端点表（METHOD / PATH / STATUS / PARSE / NOTE），最后只对「非预期失败」做硬断言。注册用户、密码、Bot 名等均使用随机后缀，日志中不输出任何 token 或密码。

### 令牌刷新

- **主动刷新**：把已保存会话改成「access token 无效 + 已过期」，下一次请求前 `CloudAuthManager.accessTokenForRequest()` 会先调 `/api/auth/token`，日志出现 `cloud token refreshed`，随后的请求 2xx。
- **401 单飞刷新**：access token 未过期但无效时，请求先拿到 401；`Api.request` 调 `refreshAfterUnauthorized()`，同一失效令牌只刷新一次，然后用新令牌原样重试一次并成功。注意 `/api/v1/health` 是公开端点，永远不返回 401，因此这一步必须用 `/api/v1/bots` 这类需要鉴权的读接口来验证。
- **刷新失败**：refresh token 损坏时刷新返回 401，`CloudAuthManager` 清空内存与 `SecureStore` 中的 `cloud.session`，触发一次「登录过期」回调，并把原始 401 抛给调用方。

## 发现并修复的 App 问题

### 1. PATCH 请求必定失败（严重）

`Api` 用 `HttpURLConnection` 发请求，而 JDK 与 Android 的 `HttpURLConnection` 都会在 `setRequestMethod` 阶段直接抛 `ProtocolException: Invalid HTTP method: PATCH`。受影响的写操作包括：

- 暂停 / 修改例程（`updateRoutineDetail`）
- 修改技能（`updateSkill`）
- 修改页面（`updatePage`）
- 修改审批规则（`updateApprovalRule`）

这些问题在单元测试和 UI 快照里都发现不了，只有打真实服务才会暴露。

修复：在 `HttpTransport.kt` 新增 `RawHttpTransport`，用一次性 socket 手写 HTTP/1.1 请求（`Connection: close`，按 `Content-Length` 或 `Transfer-Encoding: chunked` 读响应，HTTPS 走默认信任库并开启主机名校验）；`Api.requestOnce` 只对 PATCH 路由到该实现，其余方法保持 `UrlConnectionHttpTransport`。回归测试 `RawHttpTransportTest` 用本地原始 socket 服务器验证方法、鉴权头、请求体、chunked 解码与 401 透传。

### 2. 存储依赖 Android 类型，无法在 JVM 上跑生产路径

`Api` / `SecureCloudTokenStore` 原来直接依赖 `SharedPreferences` 与 Android Keystore 的 `SecureStore`。为了让 live 测试跑的是同一份生产代码而不是复制品，抽出两个窄接口：

- `KeyValueStore`（生产实现 `SharedPrefsKeyValueStore`）
- `SecretStore`（生产实现仍是 `SecureStore`，行为不变）

`Api` 保留原来的 `Api(context, cloud)` 构造器，新增接收这两个接口的内部构造器；`SecureCloudTokenStore` 改收 `SecretStore`。App 侧的存储位置、加密方式、键名全部不变。

## 数据隔离实测

用第二个全新用户访问同一台 flux-bot，记录实际行为：

| 资源 | 结果 |
| --- | --- |
| 例程 | **能看到**第一个用户的例程：服务端 `list_routines` 只按 bot 过滤，没有按云用户过滤 |
| 技能 | **能看到**第一个用户的技能：技能库是全局共享的 |
| 共享用户记忆 | 看不到第一个用户的日志：按云用户正确隔离 |

测试对「用户记忆隔离」做硬断言；例程与技能目前只记录实际行为，不阻断，因为是否按账号隔离属于服务端设计决定。

## 服务端差距

1. **`GET /api/v1/dsh/models` 返回 404**。App 的模型列表页会调这个路由，服务端当前没有实现（或路径不同）。这一项在测试中标记为预期失败，不阻断构建，但真机上该页面会拿不到数据。
2. **例程列表未按云用户隔离**：`/api/v1/bots/{bot}/routines` 只按 bot 维度过滤。多个云账号共用同一台 bot 时会互相看到例程。
3. **技能库全局共享**：`/api/v1/skills` 没有用户维度，任意登录用户可读可删他人技能。
4. **`/api/v1/health` 不需要鉴权**：App 无法用它探测登录态是否还有效；需要鉴权的读接口（如 `/api/v1/bots`）才能触发 401 刷新链路。
5. **技能名只接受 ASCII**（探测时观察到的服务端校验）：非 ASCII 名称会被拒绝，App 侧创建技能时若允许中文名会收到服务端错误。

## 已知限制

- 只覆盖 HTTP 契约与解析，不覆盖 UI 渲染；界面层由 Paparazzi 快照测试负责。
- live 测试会真实创建并删除 Bot / 技能 / 例程 / 日志，只能打测试环境，不要指向生产。
- 未覆盖 WebSocket / SSE 流式会话与文件上传下载。
